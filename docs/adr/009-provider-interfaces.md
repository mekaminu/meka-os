# ADR-009: Provider interfaces for external services

**Status:** Accepted, 2026-10-01. This follows the owner's amendment: nothing hard-coded to Gmail or any one provider.

## Decision
Each external capability is an interface in `core/providers` (shared types) with adapters in `backend/` (server-side OAuth) or in the platform apps (on-device APIs).

```
interface EmailProvider    { listChanges(cursor), getMessage(id), send(draft, idemKey), modifyLabels(id, add, remove), archive(id) }
interface CalendarProvider { listCalendars(), listEvents(range, cursor), upsertEvent(event, idemKey), deleteEvent(id) }
interface ContactsProvider { listChanges(cursor), get(id) }
interface FileProvider     { list(folder, cursor), fetch(ref), put(blob, idemKey) }
interface SportsProvider   { teamFixtures(teamRef, range), fixture(id) }       // poll + diff; changes emit FixtureChanged
interface NewsProvider     { fetch(topic, since) }                              // clustering is ours, not the provider's
interface MessagingChannel { capabilities(); ingest(event); reply(threadRef, text, idemKey) }
```

- Every mutating call takes an idempotency key.
- Every adapter declares `ProviderCapabilities`: read, write, push-vs-poll, rate limits and quirks. The UI never offers what the adapter can't do.

| Calendar | Google Calendar and Microsoft Graph (`GoogleCalendar`, `MicrosoftCalendar`) | Read-only by default. **Calendar editing (2026-10-08):** per account, only after the owner taps Allow editing, the sign-in also asks for `CalendarProvider.writeScope` (Google `calendar.events`, Microsoft `Calendars.ReadWrite`); the server records `can_edit` only when that scope was actually granted, and Stop editing clears it at once. Writes are allowed only on accounts with `can_edit`. **Writes (2026-10-08, slice 2a):** `event(remoteId)` (the provider's copy, its organiser and guest count), `createEvent(draft, idemKey)` (Google: our own event id `meka<key>` in the primary calendar, so a retry gets 409 rather than a second event; Microsoft: `transactionId`), `updateEvent(remoteId, draft, changes, notifyGuests)` (PATCH of only the changed fields; Google `sendUpdates=all` when there are guests, Graph tells them itself) and `deleteEvent(remoteId, notifyGuests)`. `CalendarWriter` sends a device's `event_edit` after its 5-second undo window: never an event someone else organises, never over a provider copy that changed in what the edit touches (CLASH, their version handed back), a delete with guests only once Meka confirmed it; 401 → "Reconnect", 403 → refused, 5xx/timeouts retried from 30 s up to 30 min apart and given up after a day. Outlook notes are written only when adding (MEKA mirrors only their preview). |
| Email | Gmail (`GmailMail`) and Outlook (`OutlookMail`), Inbox autopilot slice 1a (2026-10-13) | **Gmail:** an OAuth app in "Testing" status has refresh tokens that expire after 7 days (verified). A personal-use Production-unverified app avoids this, but shows an unverified-app warning and has a 100-user cap. Restricted-scope verification isn't needed for personal use. **Microsoft Graph:** supports personal accounts. **As built (slice 1a):** Meka allowed read, organise and send-on-his-tap (2026-10-12), so the sign-in asks for exactly Google `gmail.modify` + `gmail.send` (never `https://mail.google.com/`, which can delete for good) and Microsoft `Mail.ReadWrite` + `Mail.Send`; all must be granted. `MailProvider { oauth; requiredScopes; authorizeUrl; exchangeCode; refresh; accountEmail; inbox }`: a mail account is its own server account (`gmail`, `outlook_mail`; its own KMS-encrypted refresh token, separate from a calendar sign-in on the same address) that signs in with its `oauth` provider's client and returns through that provider's existing callback; only that callback can complete its state. A `label` (PERSONAL · BUSINESS · OUTLOOK, migration V19) names what each is for. Slice 1a only checks the sign-in every 5 minutes (the inbox's counts); `listChanges`/`getMessage`, labels, archive and send (each change with an idempotency key, send only after Meka's tap) come in the next slices. **Slice 1b:** `revoke(refreshToken)` (Google's RFC 7009 endpoint; Microsoft has none for personal accounts, so the app says where to remove it); Disconnect marks the account `disconnected` (status only, no migration), wipes its token and never syncs it until Meka signs in again (label kept); Gmail's sign-in runs out after 7 days like Google Calendar's, so mail accounts get the same `context_mode/sign_in.<key>` entity, Today line and heads-up (worded for mail). **Slice 1c (headers):** `changes(token, cursor, sinceMs)` and `header(token, id)`: Gmail's cursor is a history id (from scratch: the profile's history id, then the ids of the last 60 days, sent/drafts/chats left out; then `history.list`; every touched id read as `format=metadata`), Outlook's a Graph delta link on the inbox (`$filter` on receivedDateTime, `@removed` = left the inbox); a forgotten cursor (Gmail 404, Graph 410) lists the account again. The server keeps only headers (from, subject, received, unread, in the inbox, labels, List-Unsubscribe/-Post, List-Id) for 60 days in `mail_message`/`mail_sync` (V20); never a body, never logged; Disconnect deletes them. **Slice 2a (sorting, rules only):** `MailSortRules` (core/domain, pure) puts each kept header in one of Meka's buckets (Needs you · FYI · Newsletter · Receipt/order · Notification · Promo · Junk) from headers alone: Gmail's SPAM label → Junk; gov.uk/nhs/police/sch.uk senders → Needs you, always; carriers, and order words from a list/no-reply sender → Receipt; Gmail Promotions or a list with sale words → Promo; a list → Newsletter; Gmail Social/Updates or a no-reply sender → Notification; anything a person seems to have written → Needs you with `sure = false` (the safe side; the AI looks at those in slice 2b, words only). The server stores the bucket, reason and sureness on `mail_message` (V21, additive), sorts again whenever a header is read again, and `/v1/integrations/list` carries each mail account's inbox counts as `sorted` (absent before anything is sorted). Nothing in the mailbox changes until slice 3. |

| News pictures | The feeds' own picture links (`media:thumbnail`, image `media:content`, image `enclosure`, else the first `<img>` in the description), fetched by `NewsImages` (2026-10-08) | Same rules as the feeds: plain GET of public content, nothing about Meka sent; https only, public hosts only (no loopback, private, link-local or unique-local addresses, checked on every redirect), image types only, at most 5 MB, at most 40 new pictures and 90 s per hourly refresh. **Messaging constraints (verified 2026-10-01):**
- **No unofficial WhatsApp clients.**
- **Sideload restriction:** on a sideloaded APK, notification access sits behind Android's "restricted settings" gate (Android 13+). The user must allow restricted settings in App info before granting access. Onboarding will guide this honestly.
- **OTP redaction:** Android 15+ redacts notification content for untrusted listeners when an OTP is detected. We accept that; it is desirable.
- **Replies:** replying via a notification's `RemoteInput` action is used only while the notification exists. Otherwise we fall back to copy-and-open. Reply sending is capped at autonomy Level 3 (ADR-006).
