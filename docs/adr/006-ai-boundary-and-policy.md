# ADR-006: AI boundary, policy engine and prompt-injection defence

**Status:** Accepted, 2026-10-01

## Context
MEKA OS reads untrusted content (email, messages, web, news) and can take actions (send, archive, schedule, approve). A model that has read attacker-controlled text must not be able to cause an action outside policy. Costs must stay controlled.

## Decision

### 1. Policy is code, not prompt
A deterministic `PolicyEngine` in shared Kotlin (`core/policy`) decides every action. The same code runs on device and server.
- **Input:** the `ActionRequest`, which has an action type, domain, target, provenance and reversibility.
- **Output:** `Permit`, `RequireApproval(reason)` or `Deny(reason)`.
- **Autonomy levels** are set per (domain, action):
  - 0 Observe
  - 1 Suggest
  - 2 Prepare
  - 3 Ask approval, then execute
  - 4 Execute under explicit rule
- **Hard rules that configuration cannot override:**
  - A global kill switch denies all autonomous execution.
  - Personal message sending is capped at Level 3.
  - Financial transactions and trading approvals are always Level 3 with biometric confirmation.
  - Level 4 is only for actions marked reversible and on an allowlist.
  - Daily caps apply per action type.
  - Any request whose provenance includes untrusted content may never lift its own autonomy level.

### 2. Quarantined extraction (dual-LLM pattern)
- Untrusted content passes only through extractors that have **no tools**. They output JSON validated against a versioned schema, such as `ExtractedCommitment`, with fields that are length-limited and type-checked.
- Extracted fields carry `provenance = untrusted(source)`.
- Planning and actioning components never receive raw untrusted text. Where a draft reply must quote content, the quote is a data field that is rendered, never interpreted.

### 3. Actions are proposals
- A model proposes an `ActionRequest`, which the policy decides.
- Execution goes through the idempotent executor. The idempotency key is created at approval time, and the external side effect is recorded before it is acknowledged.
- Every step writes an `AgentAction` audit record, so "Why did you do this?" is answerable.

### 4. Provider router
- `LanguageModelProvider` is an interface with implementations for on-device and cloud models. The router chooses by task type, data sensitivity, connectivity and remaining budget.
- **On-device on Mac:** Apple Foundation Models (macOS 26+, Apple silicon with Apple Intelligence on). It gives an 8K context on OS 27, guided generation with `@Generable`, and tool calling (not used by extractors). macOS 27 also adds a `LanguageModel` protocol and an optional Private Cloud Compute model.
- **On-device on Android:** ML Kit GenAI / Gemini Nano via AICore. The Prompt API is in beta, and supported devices include the Galaxy Z Fold7 and later but **not the Fold6**. A fallback is required.
- **Cloud:** small and frontier models behind the same interface. Keys live server-side only.

### 5. Cost controls
- Deterministic pre-filters run before any model: sender rules, `List-Unsubscribe`, receipt templates.
- There are per-feature token meters and a monthly budget, with a soft alert at 70% and degrade-to-local at 100%.
- Embeddings are computed on device where possible.

### 6. Evaluation
- Extraction precision is measured on a locally held labelled set (`evals/`, git-ignored data).
- No domain may move above Level 1 until precision reaches at least 90% on its eval set.

## Consequences
- **M0 contains no AI,** by instruction. M0 does contain the `PolicyEngine`, the autonomy model, the kill switch and the audit record types, with tests, so every later AI feature plugs into an enforced boundary.
- **Prompt-injection tests,** such as a malicious email asking to forward documents, run in CI from M2 onwards.

## Addendum, 2026-10-07: the activity log (AgentAction)
The audit record of §3 is live as the `agent_action` entity (`ActivityLog` in core/domain), ahead of any automatic action. Each entry holds when, what kind (REMINDED, DIGEST, CHANGED), what MEKA did and why in words (the rule or setting behind it, e.g. "Cancel-by dates · Heads-up"), the rule's machine name, the autonomy level for actions, and for a change the before and after value of every field it touched. `ActivityLog.act` is the only way an automatic action may change the owner's data: it reads each field's current value, makes the change and records both, so `undo` can restore exactly what is still as MEKA left it (a field changed since, or in conflict, is left alone; an entity MEKA created is deleted, not blanked). Entries are written by MEKA from the owner's own data, are shown as plain text only, and stay in his synced data; the text never reaches telemetry. Reminders and digests are logged from what each device actually posted; one entry per notice key across devices.

## Addendum, 2026-10-08: calendar edits in the activity log
Every change Meka makes to a real Google or Outlook calendar from MEKA (calendar editing) is listed in Activity, as the build plan's guard "every change is in the activity log" asks. These are his own taps, not automatic actions, so they are not `agent_action` entries and nothing is stored for them: each row (kind `CALENDAR`, id `c` + the edit's id) is read from the synced `event_edit` itself (`ActivityRules.calendarEditItem`), so it follows the edit as the server answers ("Moving …" → "Moved “Dentist” in Google", a refusal, a failure, a clash and Meka's answer to it), with what it changed and why ("Your edit in MEKA · editing allowed for <account>"). An edit undone in its five seconds sent nothing and isn't listed. A row offers no Undo (after the window an edit is changed again from the event). When MEKA itself proposes calendar changes later (email, AI), those go through Needs you and are logged as actions like any other.

## Addendum, 2026-10-08: the cloud key and its health check
The cloud model key (Anthropic) lives only in Secrets Manager (`meka-os-dev/ai/anthropic`, `{"api_key": …}`), read by the service at use time; `{}` or a malformed key means the AI layer is off, and every AI feature must treat "off" as a normal state (deterministic behaviour, nothing broken). The service checks the key with Anthropic's model list (`GET /v1/models`), which sends no prompt and none of the owner's data, and tells keyed devices only whether AI is on, off or failing (`POST /v1/ai/status`), never the key. The monthly spend cap is set in the Anthropic Console; the per-feature meter and budget of §5 come with the first model call.

## Addendum, 2026-10-08: the cloud provider, token meter and monthly budget
`LanguageModelProvider` (§4) exists on the server with one implementation, `AnthropicProvider` (Messages API). It is text in, text out: no tools are ever offered to a model, so a model's answer can only become a proposal the policy engine decides (§3). Each request names a feature (a short machine name such as `ask` or `extract.email`) and a tier (SMALL → the newest Haiku, FRONTIER → the newest Sonnet, from Anthropic's model list once a day, with fixed fallbacks). Every answer is metered (§5) in the `ai_usage` table per UTC month and feature: calls, tokens and list price in micro-dollars, counts only, never a prompt or answer. The monthly budget is MEKA's share of the Console cap ($20 of $40 by default, `MEKA_AI_BUDGET_USD`): from 70 % the AI status reports `alert`, at 100 % the provider refuses before calling until the 1st (degrade-to-local: today that means AI off, since no on-device model is wired yet). The Console's own spend cap remains the hard stop behind it. The apps learn the month's spend and level from `POST /v1/ai/status`, never the key.

## Addendum, 2026-10-08: Ask MEKA, the first caller
`POST /v1/ai/ask` (keyed devices only) takes a question and the device's short picture of today (`AskRules.context`: Needs you, the day's tasks, what's done and the calendar, at most 60 lines of 160 characters). Tasks are named by handles ("t1") that never leave the device's own map; no id, note, address or email is sent. The server makes one call to the SMALL tier with no tools, under the feature `ask`; the system line says the `<today>` block is data, not instructions, and the block cannot be closed from inside (angle brackets in lines are replaced). The model may only answer in words and propose MEKA's own actions from a fixed list (add, tick off or move a task, start a fast, set a timer or alarm); it cannot send, spend, trade or change calendars. The server drops any other kind and any handle it didn't send; the device checks each proposal again (`AskRules.card`: a known kind, a handle it sent, sane days and times, at most three) and asks the policy engine with `requestedLevel = SUGGEST` and provenance MODEL_FROM_UNTRUSTED whenever calendar lines were sent (other people's invitations). Each surviving proposal is a card that does nothing until the owner taps it; the tap is his own action. A chatty answer that isn't the expected JSON is shown as words with no cards. Nothing of the question or answer is stored or logged.

## Addendum, 2026-10-08: Ask's screen and taking a card back
The apps show MEKA's AI state and the month's spend from `POST /v1/ai/status` (never the key) under Ask's field; while AI is off, the budget is used up or the device isn't connected, the field opens Search instead (the deterministic path). A tapped card is the owner's own action and returns how to take it back (`AskDone.undo`): the task it added is deleted, a ticked-off or moved task is put back only while it is still exactly as the card left it (any change since, on either device, wins), the fast is thrown away while it runs, the timer or alarm is cancelled. Nothing of the question or answer is stored on the device either.

## Addendum, 2026-10-08: Talk to MEKA, the conversation
A spoken conversation is Ask MEKA with memory of the last few exchanges, nothing more powerful. Each question still makes one tool-less SMALL-tier call under the feature `ask`; the device sends the last six exchanges with it (`AskCodec.Request.history`: Meka's question, MEKA's earlier words, and the lines of what Meka confirmed after each, e.g. "Moved “Book dentist” to Tomorrow · 09:00"), and the server lays them out as alternating turns, with the `<today>` data block only in the latest one and the same cleaning (no angle brackets) everywhere. Earlier answers go back as words only: an action offered before is never offered again from history, so every card still comes from the latest answer and is checked by the device and the policy engine as a suggestion exactly as for a typed question. The conversation lives only in the app's memory while it runs; nothing of it is stored, synced or logged, on the device or the server. A spoken "yes" ("the second one", "both", "all of them") is the owner's own confirmation, the same as tapping the card (`TalkRules.reply`, pure and unit-tested; with several cards a bare "yes" makes MEKA ask which), and every change it makes shows the usual undo chip. A conversation stops by itself after twelve questions, when nothing is heard, on a goodbye, or when AI is unavailable, so background speech can't run up calls. Speech is recognised and spoken on the device; audio never leaves it and is never kept.

2026-10-08: Talk to MEKA on the Fold
The Fold listens with Android's on-device recogniser only (`SpeechRecognizer.createOnDeviceSpeechRecognizer`, English, partial results on screen). If the phone has none, MEKA says so and doesn't listen; it never falls back to a cloud recogniser, which would send Meka's voice to a third party. When English for on-device speech is missing, MEKA asks the phone to fetch it (Android 13+) and says to try again. MEKA speaks with `TextToSpeech` using the best installed English voice that works without a network (`TalkVoice.best`: British first, then quality); network voices, which would send the text away, are never chosen. The microphone permission is asked the first time Meka taps the mic, and the conversation stops when Ask leaves the screen or the app goes to the background. A spoken yes runs the confirmed cards through `MekaCore.doTalk` (each exactly as a tap, one undo bar for the lot via `undoTalk`). Barge-in on the Fold is by touch (tapping the orb while MEKA speaks stops it and listens), since the recogniser would otherwise hear MEKA through the phone's own speaker.

2026-10-08: Talk to MEKA on the Mac
The Mac listens with `SFSpeechRecognizer` (en-GB) with `requiresOnDeviceRecognition` set; if the recogniser can't work on the device (English not downloaded, which Dictation fetches), MEKA says so and doesn't listen, and never lets the request fall back to Apple's servers. macOS asks for the microphone and speech recognition the first time (usage strings say nothing is recorded or sent away; the hardened runtime carries `com.apple.security.device.audio-input`). Because the Mac's recogniser doesn't decide when a question is over, `TalkEndpoint` (pure, unit-tested) does: a 1.5 s pause after words ends the question, 8 s with nothing heard is silence, and no question runs past 55 s. The microphone's buffers go only to the recogniser and to a loudness meter for the orb; nothing is kept. MEKA speaks with `AVSpeechSynthesizer` using the best installed English voice (`TalkVoice.best` over the Mac's voices: British first, premium over enhanced over default), which always speaks on the device. A spoken yes runs through `MekaCore.doTalk` with one undo bar, as on the Fold. Barge-in is by click on the orb. The conversation stops when Ask leaves the screen or MEKA stops being the app in front. ⌥Space (Talk to MEKA in the Edit menu) brings Ask forward and starts or ends it while MEKA is in front; a system-wide shortcut is a later step.

2026-10-09: Talk without tapping the mic (slice 1)
Holding the Fold's side key (with MEKA chosen as the digital assistant app, `ACTION_ASSIST`) or a headset's button (`ACTION_VOICE_COMMAND`) opens MEKA on Ask already listening, through a trampoline activity that shows nothing. It is the same conversation as tapping the mic: the same on-device recogniser, the same microphone permission (asked the first time), the same tool-less `ask` calls and the same yes-before-anything rule; a start only opens Ask, it never acts. Anyone near the phone can speak once it listens, which is why the spoken or tapped yes and Undo stay the guard (speaker recognition isn't built). MEKA doesn't register a `VoiceInteractionService` (no hotword, no listening while closed).

2026-10-09: Talk without tapping the mic (slice 2)
MEKA also opens on Ask listening, with no tap on the mic, when (a) it is opened from the launcher while Bluetooth audio is connected (headphones, buds, hearing aids, a car's hands-free) or the phone is in car mode, and (b) the home screen's Talk widget is tapped. The rule is the core's `TalkStartRules.onOpen` (pure, unit-tested): only a launcher open counts (never a notification, another widget, a return from Recents or a rotation/unfold), and the phone's own speaker never auto-listens. Everything after that is slice 1's conversation: the on-device recogniser only, the microphone permission asked the first time, nothing acted on without a spoken or tapped yes, and every change undoable.

2026-10-09: Talk without tapping the mic (slice 3)
Two more taps start listening at once: the mic beside the bedside clock's alarm line (the Fold half folded on a table), which springs a Talk pane up over the clock, and the mic on the closed Fold's now card, which opens Ask. Both are a tap by Meka on MEKA's own screen, so they are the same as tapping Ask's mic: the on-device recogniser only, the microphone permission asked the first time, nothing acted on without a spoken or tapped yes, every change undoable. At the bedside, quiet hours' screen dimming lifts only while the Talk pane is up.

2026-10-09: Talk without tapping the mic (slice 4, the Fold)
"Listen when I open MEKA" (Ask → More → Talk → When I open MEKA; off by default; kept on the phone, never synced): a launcher open (never a notification, a widget or a return from Recents) with the microphone already allowed opens Ask and listens, after a 300 ms room check. The room check reads the microphone into memory and keeps only a number (an uncalibrated, about-dBA level, `TalkOnOpenRules.roomLevel`); above about 60 it doesn't listen and says "Too noisy — tap to talk". Otherwise a quiet chime and the same on-device recogniser as the mic, for up to 6 s: nothing said by then and listening stops and Today comes back. An open never asks for the microphone (turning the setting on does). Everything heard goes through the same yes-before-anything as the mic; nothing about autonomy changes. The Mac's version is below.

2026-10-09: Talk without tapping the mic (slice 5, the Mac)
The Mac gets "Listen when I open MEKA" (Ask → More → Talk; off by default; kept on the Mac in UserDefaults, never synced). Opening MEKA counts only when it is a plain launch (AppKit's default launch: from the Dock, Finder or Spotlight, never to open a link, a file or a notification) or a Dock click that brought MEKA forward from the background (`TalkOnOpenRules.reopenFromBackground`: not yet active, or activated within the last second); clicking the Dock while MEKA is already in front doesn't. It also needs the microphone and speech recognition already allowed (`TalkOnOpenRules.macOpenStart`): an open never asks; turning the setting on does. Then Ask comes forward and AVAudioEngine reads the microphone for 300 ms, keeping only a running sum of squares and a count (`TalkOnOpenRules.levelAt`, the same level as the Fold's); above about 60 it says "Too noisy — click to talk" under the resting orb, else the system's Tink at 30 % and the same on-device-only recogniser as the mic for up to 6 s, Today coming back if nothing is said. Everything heard goes through the same yes-before-anything; nothing about autonomy changes.

## Addendum, 2026-10-09: requests from people Meka watches (quarantined extraction, the first)
`POST /v1/ai/message-request` (keyed devices only) is the first extractor in the sense of §2: one message at a time, from a person Meka chose (the family list or Work mode → People → Watch for requests from; 1:1 chats only unless he names a group), as the text the notification showed, the sender's label as the notification named them, the time it came, the date and Meka's work days in a line (`MessageRequestCodec.Request`; at most 2,000 characters of text). Never a phone number, a contact, another chat or anything else of the phone's. The server makes one SMALL-tier call with no tools under the feature `extract.message`, the message inside a `<message>` data block it can't close, and reads back at most three proposals of four kinds (task · work_from_home · event · reminder) with the message's own when-words; anything else, or an answer that isn't the JSON, is no proposals. Nothing of the message or the answer is stored or logged on the server. The device checks every proposal again (`MessageRequestRules.check`): a known kind, a clean one-line title of at most 80 characters, the day resolved again from the message's own words (`RequestDates`, the same reading as Add event's typing; the model's date is used only when the words don't read), never in the past or more than a year ahead. Voice notes and bare photos are never sent; a voice note becomes "Listen to Wife's voice note" with no AI. A proposal is only ever a Needs you card (Add · Change · Not a task); nothing is added, no work day changed and nothing is replied to, marked read or dismissed without Meka's tap.

## Addendum, 2026-10-09: the messages assistant (triage, the second extractor)
`POST /v1/ai/message-triage` (keyed devices only) sorts one message into a lane, under the same terms as the request reader above: one message at a time, its text as the notification showed it, the sender's label, the group's name only when a group message names Meka, the time, the date and his work days (`MessageTriageCodec.Request`); never a number, a contact or another chat. Before any AI the device routes each message (`MessageTriageRules.route`): group chatter that doesn't name Meka goes to the group digest with **no AI** (or is left alone / ignored by the group's mode), voice notes become a reminder, bare photos and anyone or any group on the "never send to AI" list are FYI with no AI. The server makes one SMALL-tier call with no tools under the feature `triage.message`, the message inside a `<message>` block it can't close, and reads back one lane (needs_reply · action · fyi; anything else, or an answer that isn't the JSON, is FYI), a gist, a reply draft only for needs_reply and proposals only for action (the request reader's four kinds, checked again by `MessageRequestRules.check`; none left → FYI). A draft is text shown to Meka: the device keeps it only as one paragraph of at most 400 characters with no link, email address or long number (`MessageTriageRules.cleanDraft`), so a message can't put an address in his mouth, and it is sent only by his tap through Android's own notification Reply action (Level 3, never automatic, family included). Nothing of the message or the answer is stored or logged on the server.
**Replying (messages slice 3):** the Fold holds each message's notification Reply action (RemoteInput) in memory only while the notification shows (`LiveReplies`); Send on a Needs a reply card fills it with the words on the card, on Meka's tap only (Send all: one tap over short 1:1 replies, never into a group). No WhatsApp library and no automatic send, family included; a card answered on either device records only sent · seen · dismissed. The Mac never sends (Copy reply).

## Addendum, 2026-10-09: the group digest's gist (messages assistant, slice 4b)
`POST /v1/ai/group-digest` (keyed devices only) summarises the busy groups in one digest. It runs at most once per digest time (12:30 and 18:30, the first time the Fold's listener or Needs you notices the digest is due) and carries, for at most six groups that each have five or more new messages since Meka last caught up, the group's name and its latest 40 lines as the notifications showed them (sender's label, time, text cut to 300 characters), with the date and time (`GroupDigestCodec.Request`). Never a number, a contact, a 1:1 chat, a group Meka set to Normal or Ignore, or anything kept from the AI. The server makes one SMALL-tier call with no tools under the feature `digest.groups`, each group inside a `<group>` block within a `<digest>` block that can't be closed from inside, and reads back a gist per group and at most three asks (needs_reply, or action with the request reader's four kinds); groups that weren't sent, unknown lanes and an answer that isn't the JSON are dropped. The device checks it again (`GroupGistRules.check`): a gist is one line of at most 160 characters; an ask must come from someone who wrote in that group and becomes a Needs you card only — Needs a reply **with no draft** (a reply into a group is Meka's to write; the card opens the chat) or request cards quoting the ask's gist. Nothing of the messages or the answer is stored or logged on the server; on the devices only the gist, counts and senders' labels are synced (`group_gist`, ADR-008), and the chatter itself stays sealed on the phone. With MEKA's AI off or the month's budget spent the digest's cards are still written, without gists.

## Addendum, 2026-10-09: kept from MEKA's AI (messages assistant, slice 5)
Work mode → Messages on the Fold keeps a "never send to MEKA's AI" list (people and groups, by name; sealed in `CaptureStore`, never synced). A person or group on it is never part of an AI request: their 1:1 messages and mentions become a local FYI card (`MessageTriageRules.route` → `LocalFyi`), a kept group is left out of the digest's gist call, and a kept person's lines are dropped from any group's lines in that call (`GroupGistRules.groups`). A kept group still gets its digest card on the phone and its synced card (title, count, who wrote) with no gist.

## Addendum, 2026-10-10: "play my messages" in Talk (call assistant polish 8c)
A spoken request for voice messages ("play my messages", "any voice messages?", "who called?") is recognised on the device by `VoicePlaylistRules.isPlayRequest` before anything is sent: it is never an AI call, and it doesn't count towards the conversation's question cap. The app plays the voice messages in the after-work summary it shows (MEKA's own lines through MEKA's voice; each caller's recording from MEKA's server over the same signed request as ▶ Play, played from memory and let go; their words when no recording is kept), then listens again. Nothing is marked, cleared or sent; the conversation remembers only "Played Meka's voice messages from the call assistant." so a follow-up question has context, never the callers' words.

## Addendum, 2026-10-10: Suspected spam (call assistant polish 8b c, the third extractor)
Once a voice message's words are settled (Amazon Transcribe, or Twilio's as the fallback), MEKA's server asks the SMALL tier once, with no tools, under the feature `extract.callscam`, whether they sound like a scam or nuisance call (`CallScamCheck`). Only the words are sent, inside a `<voicemail>` block the caller can't close (angle brackets replaced), at most 2,000 characters: never the caller's number, Meka's name for them or anything else of his. It asks only for a real number that isn't blocked, hasn't been flagged and hasn't been cleared with Not spam, and only when the message has at least three words; AI off, an empty budget or an answer that isn't `{"scam": true|false, "why": …}` flags nothing. A yes is a suggestion, never an action: the number goes on Suspected spam (`blocked_caller.suspected`, ADR-008) with the reason (one line, at most 80 characters, no links), an Activity entry says so, and Meka chooses Block or Not spam on either app. Until he does, the Fold's screening sends that number's calls to the assistant instead of ringing, which only ever means a caller can leave a message (family, always-notify, contacts and anyone Meka called lately still ring). The model's answer can't raise its own autonomy: nothing is blocked, sent or deleted because of it. Nothing of the words or the answer is stored or logged on the server beyond the flag and its short reason.
