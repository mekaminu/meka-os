# ADR-008: Domain model — Household and actionable primitives

**Status:** Accepted, 2026-10-01

## Context
- Everything lives in one life graph.
- Meka is the only user for MVP/V1, but his wife may become a real user. Family entities must therefore belong to a household, not to one user.
- Task is not the only actionable primitive.
- The owner has asked for Decision, Waiting For and Someday/Maybe as first-class concepts.

## Decision

### Tenancy
- `Household` is the tenancy and sync boundary. Every entity carries `householdId`.
- `Person` is anyone in the graph: family, friends, the coach, a colleague.
- `Principal` is a person who can sign in. There is one today; the model allows more.
- `Membership(principalId, householdId, role)` holds the role: `OWNER`, `ADULT` or `CHILD_PROFILE` (non-login).
- Visibility is per entity: `HOUSEHOLD` (shared) or `PRIVATE(principalId)`. M0 writes everything as `PRIVATE(owner)` except family entities, so that sharing later is a policy change, not a migration.

### Actionable primitives
These share an `Actionable` core: `id`, `householdId`, `title`, `lifecycle`, `ownerPersonId`, `dueAt?`, `priority`, `goalIds`, `provenance`, `createdAt`, `updatedAt`.

| Entity | Purpose | Key fields |
|---|---|---|
| **Task** | Something I will do | `estimateMinutes`, `scheduledAt`, `contextModes`, child `ChecklistItem`s |
| **Commitment** (`direction = OWED_BY_ME`) | Something I promised someone | `counterpartyPersonId`, `sourceRef`, `confidence`, `lastInteractionAt` |
| **WaitingFor** (`direction = OWED_TO_ME`) | Something I'm waiting on from someone or something | `counterparty`, `expectedAt`, `lastInteractionAt`, `followUpAt`, chase suggestions |
| **Obligation** | A dated or recurring duty attached to an entity (MOT, boiler, subscription, school form, warranty) | `subjectRef`, `recurrence`, `cost`, `documentRefs`, `leadTime` |
| **Decision** | A decision made, so it isn't re-made | `statement`, `decidedAt`, `rationale`, `context`, `relatedGoalIds`, `relatedPersonIds`, `reviewAt`, `status` (ACTIVE / SUPERSEDED / REVISITING), `supersedesDecisionId`, `provenance` |
| **Goal** (MVP-light) | Why activities matter | `target`, `horizon` (SHORT/MEDIUM/LONG), `priority`, `progress`, related tasks/habits |
| **Habit** (MVP-light) | A recurring behaviour | `targetFrequency`, `preferredTiming`, completion history as child `HabitCompletion` entities |
| **Event** | Something at a time (calendar, fixture, class) | `startsAt`, `endsAt`, `timezone`, `location`, `source` |

Commitment and WaitingFor are one table (`commitment`) with a `direction` field. They are the same shape viewed from opposite sides, and "what am I waiting for from the school?" and "what have I promised the school?" are one query.

**Lifecycle** is shared by all actionables:
- States: `INBOX`, `ACTIVE`, `SOMEDAY`, `WAITING`, `DONE`, `CANCELLED`.
- **Someday/Maybe** is `lifecycle = SOMEDAY` plus a `somedayKind` (IDEA, PURCHASE, PROJECT, TRIP, BOOK, RESEARCH, APPLICATION, HOME_IMPROVEMENT).
- The planner's capacity calculation excludes SOMEDAY, and the resurfacing agent (V1) proposes promotions.

### Graph relationships
- **`Relation`** entities are first-class and typed: `(fromRef, type, toRef, provenance)`. Examples: `Logan -[CHILD_OF]-> Meka`, `Logan -[MEMBER_OF]-> Norwich FC U10`, `Commitment -[DERIVED_FROM]-> Message#…`, `Task -[SERVES]-> Goal`.
- **ContextMode** holds the modes Work, Personal, Focus and Quiet, which are user-visible. Commute, Travel and Training are inferred states.
- **Provenance** records the source (user, voice, notification:package, email:messageId, agent:actionId), trust (`TRUSTED_USER`, `UNTRUSTED_EXTERNAL`, `DERIVED`) and the extractor model/version.

### Schema versioning
- Every entity type has a `schemaVersion`, and ops carry the writer's version.
- Readers upgrade ops from older versions. Unknown newer fields are preserved, not dropped.

## Consequences
M0 implements the full generic sync substrate and these entity types for real:
- `Task`
- `ChecklistItem`
- `Household`
- `Person`

The other types are defined as field schemas and merge policies, so the planner and UI can adopt them without sync changes.

## Addendum, 2026-10-06: repeating tasks
A repeating Task is a series of occurrences rather than one task that rolls forward. Each occurrence carries `recurrence` (an iCalendar RRULE subset), `seriesId` and `occurrenceDay` (local epoch day); a snooze sets `deferredToDay` without changing the series day. Completing or skipping an occurrence writes the next one under the deterministic id `<seriesId>.d<epochDay>`, so concurrent completions on two offline devices converge on a single next occurrence and history stays one task per day. Rules this version can't read are kept as text and not acted on. Obligation (`recurrence`) will reuse the same rule type.


## Addendum, 2026-10-06: lists
Waiting for, Someday and Decisions are live (`Lists` in core/domain). Waiting for uses `commitment` with `direction = OWED_TO_ME` and `lifecycle = WAITING` (DONE when it arrives); `followUpAtMs` is the chase date and `lastInteractionAtMs` the last chase. Someday stays a Task with `lifecycle = SOMEDAY` and `somedayKind`. A Decision's `status` moves ACTIVE → REVISITING → ACTIVE, or to SUPERSEDED when a new decision with `supersedesDecisionId` replaces it; superseded decisions are kept. Chase and review dates are whole local days, stored as 09:00 local on that day so they read back as the same day on every device and across clock changes. Concurrent edits to user-visible fields of these entities resolve deterministically; any later edit clears the conflict (they are not yet offered as choices in Needs you).

## Addendum, 2026-10-06: goals and habits
Goals and Habits are live (`Goals` in core/domain), still MVP-light. A Habit has `targetPerWeek` (1–7, ISO weeks Monday to Sunday), `preferredTiming` (MORNING / AFTERNOON / EVENING / ANYTIME), `minutes` (added field) and an optional `goalId`. Each tick is a `habit_completion` with the deterministic id `<habitId>.d<epochDay>` and fields `habitId`, `day`, `done`, `atMs`, so ticks of the same day on two offline devices converge on one entity and unticking is `done = false` (LWW). Pace and streaks are computed, never stored: the week's target is pro rata in the week a habit was added; a daily habit's streak counts days, any other target counts weeks that met it. A Goal's progress is counted from linked Tasks (`goalId`; done ÷ linked, Someday and cancelled excluded) and linked Habits (this week's share), averaged per item; with nothing linked it is the hand-set `progressPct`. Finishing a goal sets `lifecycle = DONE` (terminal wins); deleting one unlinks its tasks and habits first. The planner makes room for habits that are behind or due today, before tasks, in their preferred part of the day; habit blocks are part of the suggestion only.

## Addendum, 2026-10-06: fasting
Two entity types were added (additive): `fast` (`startedAtMs`, `targetHours`, `endedAtMs` — Null while running — plus provenance) and `fasting_plan` (one entity, id `default`: `targetHours`, `eatingStartMin`, `eatingEndMin` as local minutes of the day; the window may cross midnight). All fields are LWW; discarding a fast sets `deleted` (true wins). Fasts started on two offline devices are both kept: the earliest open fast is the current one, ending ends every open fast, and history merges overlapping finished fasts so nothing is counted twice. History and averages are computed, never stored; a fast counts on the local day it ended. `Fasting.plannerMeals` gives the planner meal blocks (break the fast at its goal when that lands today; the last meal before the eating window closes) that are kept free like events and shown, not applied.

## Addendum, 2026-10-06: evening shutdown
No new entity type. The shutdown is one `context_mode` entity with the fixed id `shutdown` and two LWW fields: `shutdownDay` (the local epoch day it was done) and `shutdownAtMs`. A shutdown counts only for the day it names, so a stale value from an offline device never hides today's card. Carrying an item over is the existing per-occurrence snooze (`deferredToDay`, times of day kept); skipping and Someday are the existing commands. "Left from today" (open tasks Today shows, plus ones planned for an earlier day that were never done) and the tomorrow preview (events, tasks whose day, plan or due date is tomorrow, work hours) are computed, never stored.

## Addendum, 2026-10-06: renewals and bills radar
Obligation is live (`Renewals` in core/domain), entered by hand. Fields (additive): `kind` (MOT, CAR_TAX, INSURANCE, BOILER, SUBSCRIPTION, BILL, LICENCE, WARRANTY, OTHER), `dueAtMs` (the shared actionable field, a whole local day stored as 09:00 local like chase dates), `recurrence` (the task RRULE subset; the apps offer monthly, every 3 months and yearly, anchored on the due day, and keep any other rule as text), `costMinor` + `currency` (pence, GBP), `leadDays` (how early it shows; defaults by kind), `cancelByAtMs` (UserVisible), `subjectLabel` (free text until it can reference People or Vault entities) and `lastDoneAtMs`. An obligation rolls forward in place rather than as a series: "renewed" sets `dueAtMs` to the rule's next day after the current one and moves `cancelByAtMs` by the same number of days; two offline devices compute the same values, so they converge without a conflict. A one-off is DONE; "cancelled it" / "stop tracking" is CANCELLED (kept). Where it stands (overdue, cancel-by within 7 days, inside the lead time, later) and the monthly/yearly cost of repeating items are computed, never stored. Renewals are part of `ListsView`, so what needs doing counts in Needs you.

## Addendum, 2026-10-06: notification settings (Quiet)
No new entity type. Quiet is the `context_mode` entity with the fixed id `quiet`, three LWW text fields: `quietHours` ("on;start;end" in local minutes; default 22:00–07:00), `digestTimes` ("750,1080"; empty for no digests) and `noticeTiers` ("SHUTDOWN=DIGEST,…": sources the owner moved to a lower tier; a raised tier is ignored when read, so synced data can never make something interrupt more than its default). Notices themselves are never stored: the governor (`Governor` / `NoticeSources` in core/domain) derives them from lists, renewals, fasting, the shutdown and Today on every evaluation. What each device has posted, and what it posts at all (everything / digests only / off), stays on that device.

## Addendum, 2026-10-06: morning brief
No new entity type. Reading the brief ("Got it") is one `context_mode` entity with the fixed id `brief` and two LWW fields: `briefSeenDay` (local epoch day) and `briefSeenAtMs`; like the shutdown, it counts only for the day it names. *Addendum 2026-10-08 (additive):* two more LWW text fields, `briefSeenBy` (the reading device's id) and `briefSeenOn` (its app's name for itself, "Mac" or "Fold"), so the other device can say "Brief read on your Mac"; and once the morning has started, only a read at or after that morning's start puts the card away (a read at 00:30 was last night's brief). The brief itself (today's events and open tasks in time order, waiting-for items, renewals and decisions that need doing, habit pace, a running fast) is computed from the other views, never stored. News headlines will be added by server-side ingestion (NewsProvider, ADR-009) in a later slice.

## Addendum, 2026-10-06: news headlines
One entity type was added (additive): `headline` (`title`, `url`, `source`, `topic`, `publishedAtMs`, `removed`), written only by the server's news ingestion, so every field is LWW and never conflicts (like `event`). The server keeps a fixed set of slots per topic (entity id derived from account, topic and slot), so the number of headline entities is bounded; a slot is rewritten only when a different story takes it, and an empty slot has `removed = true`. Which topics the brief shows is the `context_mode` entity `news` with one LWW field, `newsTopics` (comma-separated topic ids; unknown ids ignored when read, empty means no news). Headline text is untrusted (ADR-006): the apps show it as plain text and open a link only when it is https.

## Addendum, 2026-10-06: weekly review
No new entity type. "Done reviewing" is one `context_mode` entity with the fixed id `review` and two LWW fields: `reviewedWeek` (the Monday of the reviewed week, as a local epoch day) and `reviewedAtMs`; it counts only for the week it names. The review itself (tasks finished in the week by `completedAtMs`, habit ticks against the week's target, fasts by end time, waiting-for items received, decisions made, obligations done by `lastDoneAtMs`, what was planned or due and is still open, and the week ahead) is computed from stored data, never stored. Which week the screen shows is a per-device screen choice, not synced.

## Addendum, 2026-10-06: interruptions count
One entity type was added (additive): `interruption_day` (`day`, `device`, `critical`, `action`, `headsUp`), one per device per local day with id `<deviceId>.d<epochDay>`, written only by the device named in its id, so every field is LWW and two devices never conflict. Counts only: no titles, sources or text. When counting began is the `context_mode` entity `interruptions` with one LWW field, `countingSince` (a local epoch day, written once, the first time any device could post). The weekly review adds the counts up across devices for its week.

## Addendum, 2026-10-06: event notes and call links
Two fields were added to `event` (additive, LWW, server-written like the rest): `description` (the event's notes as plain text, at most 2,000 characters; the server strips Google's HTML and keeps a link's address beside its text; Microsoft sends a plain preview) and `joinUrl` (the provider's own video-call link — Google `hangoutLink` or a `video` conference entry point, Microsoft `onlineMeeting.joinUrl` — mirrored only when https). Neither is written for an event that has never had one, so existing events gain no ops. Notes are untrusted (ADR-006): the apps show them as plain text only. The event detail's Join button uses `joinUrl`, or else the first https link to a known call service (Meet, Teams, Zoom, Webex, Whereby, FaceTime) in the location or notes, matched by host (the host or a subdomain; no user-info or ports).

## Addendum, 2026-10-07: activity log
One entity type was added (additive): `agent_action` (`atMs`, `kind`, `summary`, `detail`, `why`, `source`, `level`, `changes`, `undoneAtMs`, `undoNote`), all LWW: an entry is written once when MEKA acts and afterwards only its undo marks change. Ids: reminders `n` + FNV-1a-64 of the notice key and digests `g` + FNV-1a-64 of day and digest name (so two devices posting the same notice write one entry); actions a random id. `changes` lists each touched field as tab-separated type, id, field, before, after (values tagged `-`, `t:`, `i:`, `b:`; text escaped), read all or nothing. An entity MEKA created records `deleted` false-from-true so undoing deletes it. What the Activity screen shows (the last 30 days by day, the week's counts) is computed, never stored.

## Addendum, 2026-10-07: calendar actions
Events stay a read-only mirror written by the server. What Meka does with an event in MEKA lives beside it. One entity type was added (additive): `event_mark`, one per event with the event's id, fields `hidden` (Bool) and `hiddenAtMs`, all LWW (the latest tap on any device wins). Hidden events are left out of Today's timeline, Plan my day, the brief, the evening shutdown and the weekly review; the Calendar tab lists them under their day so they can be shown again. Search still finds them. One field was added to `task` (additive): `eventId`, the event a prep task is for. A prep task's id is `p<eventId>`, so adding it twice, or on two offline devices, makes one task; adding it again after it was deleted or finished brings the same task back (deleted false, ACTIVE, completedAt cleared). It is due at the event's start and planned 30 minutes before it for 15 minutes (unplanned when that time has passed; an all-day event's is due 09:00 local on its first day).

## Addendum, 2026-10-07: event reminders
Two fields were added to `event_mark` (additive, LWW like the rest): `remindMin` (remind me this many minutes before, 1–240; null for none) and `travelMin` (Leave by: how many minutes it takes to get there, 1–240; null for none). Nothing is stored per reminder: the notices are derived on every governor evaluation (`ReminderRules.notices`), keyed by the event's id, its start and the minutes, so a moved event reminds again at its new time and each device posts a reminder once. Hidden, all-day and started events don't remind; a leave-by needs a place (not just a link). The travel time is Meka's own; no maps service is asked.

## Addendum, 2026-10-07: the event's web page
One field was added to `event` (additive, LWW, server-written like the rest): `webUrl`, the event's own page in the provider's web app (Google `htmlLink`, Microsoft `webLink`), mirrored only when https and at most 2,000 characters (a longer one is left out, never cut). Unlike notes, every Google and Outlook event has one, so each mirrored event gains one op at the first poll after the deploy, then none. The apps offer "Open in Google Calendar" / "Open in Outlook" only for a link on that provider's own web host (`calendar.google.com`, `www.google.com/calendar/…`; `outlook.live.com`, `outlook.office.com`, `outlook.office365.com`), so Meka can change the real event there; MEKA itself still never writes to his calendars.

## Addendum, 2026-10-07: extended fasts
Two fields were added to `fast` (additive, LWW like the rest): `kind` (`"extended"` for a fast of days; absent for the daily-window kind, so every earlier fast stays one) and `goalAtMs` (the goal as a moment, "until Friday 18:00"; absent when the goal is `targetHours` from the start). An "until" fast still writes `targetHours` (rounded up), so a build that predates these fields shows it as a fast with an hours goal. The goal range is now 1–240 hours (was 1–72); an older build caps what it shows at 72 h but never rewrites the value. Changing the goal of an "until" fast to hours clears `goalAtMs`. History, the streak and the heat strip are derived on every read; nothing new is stored for them.

## Addendum, 2026-10-07: a fixture's kick-off moved
Two fields were added to `event` (additive, LWW, server-written): `movedFromMs` (the kick-off before the move) and `movedAtMs` (when the server saw it). Written only for the fixtures feed, only when an existing, not-removed, timed fixture's start changed while the old start was still ahead; never cleared (a later move overwrites both). The apps turn them into a "Kick-off moved" heads-up through the notification governor (`FixtureMoves`); events polled before this, and every non-fixture event, never carry them.

## Addendum, 2026-10-07: UK bank holidays
One server-written `context_mode` entity, id `bank_holidays` (additive, LWW; the apps never write it): `dates` ("2026-12-25=Christmas Day;…", sorted, from 1 January of last year on) and `source` ("GOV.UK · England and Wales"). The server mirrors GOV.UK's public `bank-holidays.json` (England and Wales; no sign-in, nothing about the household sent) weekly through a `bank_holidays` integration account every household follows, like the fixtures and news feeds, and writes only when the list changed (then wakes the devices). Work mode treats a listed day as a day off: a shift that starts on it doesn't count (a night shift belongs to the day it starts on), "next shift" skips it, the brief and the shutdown's tomorrow preview say "Christmas Day · no work", and the evening shutdown starts at 18:00. The Work switch still overrides it. Unreadable entries are skipped; a list that can't be read leaves the last one in place.

## Addendum, 2026-10-07: hide a calendar from Today
One entity type was added (additive): `calendar_mark`, one per calendar with the id `c` + FNV-1a-64 of `calendar:<key>`, where the key is `provider|account (lower case)|calendar name` (the fixtures feed is one calendar, `fixtures||`). Fields, all LWW (the latest switch on any device wins): `calendarKey`, `calendarLabel` (its name when hidden, so Calendars can list it with no events in the mirror), `hiddenFromToday` (Bool) and `hiddenAtMs`. A hidden calendar's events leave my day exactly as "Hide from my day" does for one event (Today's timeline and All day group, Up next, Plan my day, the brief, the shutdown, the review); the Calendar tab and Search still show them, and a reminder set on one of its events still comes. Nothing is written to the event marks of its events, so showing the calendar again restores them all. Which calendars exist (Calendars' "On Today" list) is derived from the mirror on every read.

## Addendum, 2026-10-07: the after-work summary on the Mac
One entity type was added (additive): `held_message`, one per WhatsApp message, text or missed call the Fold's listener held during work mode, so the Mac shows the same "While you were at work" summary (Needs Meka #10, approved 2026-10-07: synced through Meka's own server and stored like his other data). The id is `h` + FNV-1a-64 of `held:<capture id>` (the capture id is the existing deterministic one from app, kind, sender, chat, time and a text hash), so a re-post, a second hold or a reinstall makes no second entity. Fields, written once by the Fold: `app`, `kind`, `person`, `text` (display only, untrusted per ADR-006), `conversation`, `atMs`, `family` (on the family list when held; the lists stay on the Fold). Done on either device writes `cleared = true` (TrueWins, so a clear is never undone by a concurrent edit), `clearedAtMs`, and blanks `text`; holding a cleared item again is a no-op. Both apps show the items not cleared from the last 7 days (at most 500), grouped as before (urgent, family, latest). The Fold keeps its sealed local copy for spotting re-posts and the people lists; the summary both apps show is the synced one.

## Addendum, 2026-10-07: the GitHub build in Activity
No new entity type or field: `agent_action` gains the kind `PUBLISHED`, written by the server (device `server`) when a phone build published by the release-only publisher (`github-build`) is complete. Id `r` + FNV-1a-64 of `release:<platform>:<build number>`; fields `atMs`, `kind`, `summary` ("GitHub build published build 412"), `detail` ("MEKA 0.1.412 · 24.3 MB · install it from Today on the Fold"), `why`, `source` (`release:github-build`), built by `ActivityRules.releaseFields` in the core. Op ids are fixed per build and field (`srvrel<id><field>`), so a build is recorded once however often it is reported. Nothing to undo. Builds a household device publishes (the Mac's manual fallback) aren't listed. Apps that don't know a kind skip the entry.

## Addendum, 2026-10-07: the call assistant's switch
One field was added (additive) to the `context_mode` entity `work`: `callAssistant` (Bool, last writer wins; absent = off). Either app turns the call assistant on or off; the Fold's call screening reads it with the work-mode state. The people lists' phone numbers (picked with each name, so calls can be recognised) stay in the Fold's sealed local file with the lists and are never synced; the few minutes of declined callers kept for the repeat-caller rule (number keys and times only) stay in the Fold's private preferences.

## Addendum, 2026-10-08: the call assistant's voice messages
No new entity type. `held_message` gains the kind `VOICE_MESSAGE` and one field (additive): `urgent` (Bool, TrueWins; absent = no), set when the caller answers "is it urgent?" with 1 or a yes. Voice messages are written by the server (device `server`) from the phone service's webhooks: id `h` + FNV-1a-64 of `held:voice:<provider>:<call id>`, fields `app` = PHONE, `kind`, `person` (the caller's number as the network gave it, or "Withheld number"; the server has no people lists, so `family` is false and the Fold shows a listed caller by name and ranks them as family by number), `atMs`, later `text` (the phone service's transcript, display only, untrusted per ADR-006; not written once the item is cleared). Op ids are fixed per call and field (`srvvoice<id><field>`), so a retried webhook writes nothing more. An urgent message (by the answer, or by the words "urgent"/"emergency" in its transcript) wakes the household's devices at high FCM priority — the push still carries only `{"t":"sync"}` — and the Fold rings it through on its "Urgent while at work" channel once, within an hour of the call. Apps that don't know the kind skip the item (unknown kinds are skipped).

## Addendum, 2026-10-08: news sources and the News place
Two fields were added (additive). `headline.summary`: the feed's own description as plain text (at most 500 characters; never written for a slot that never had one); `headline.source` now names the publisher per item (an aggregator such as Google News names each story's paper). `context_mode/news.newsTopicsKnown`: the topic ids that existed when `newsTopics` was last written, so a topic added later follows its default for a choice made before it existed (absent = the first nine BBC topics). New topic ids `barca`, `spain`, `ai`, `tech` (ids are wire format: never renamed). A second news account (`news_more`) mirrors ten slots per topic instead of four; slot ids stay per account, topic and slot.

## Addendum, 2026-10-08: news pictures
One field was added (additive): `headline.image`, the key under which the household's own server keeps the story's picture (32 lowercase hex characters: the first half of the SHA-256 of the picture's address). Never the publisher's address: devices fetch pictures from their own server only (`POST /v1/news/image {"key"}` → `{"data": base64 JPEG}`, keyed devices only), and the apps ignore a value that isn't such a key. Never written for a slot that never had a picture. The pictures themselves are not anyone's data and are not synced: a server table `news_image` (migration V7, additive) holds one small JPEG per key, shared by every household, deleted three days after the last feed that mentioned it.

## Addendum, 2026-10-08: the Gym (booked habits)
Five fields were added (additive, all LWW). `habit.bookSlots`: MEKA books the habit's sessions into the week around the calendar and work hours (`SessionRules`, derived on each device, nothing stored about the booking itself). `habit.rotation`: the rotating labels as `Push|Pull|Legs` (absent or empty for none). `habit_completion.missed`: "Didn't go" on a booked session (the week is rebooked; `done` wins over it when both are set). `habit_completion.label`: the rotation label the session was. `habit_completion.note`: an optional one-line note (at most 80 characters). Older apps ignore all five: a booked habit there is an ordinary habit, and a missed day an unticked one. A sixth (2026-10-08, additive, LWW): `habit.appLink`, a link to the workout app (`https://hevy.com`), offered as "Open Hevy" on Today's card; only http(s) addresses with a real host and no login part, at most 300 characters (`SessionRules.cleanAppLink`, checked again on read, so a bad synced value is ignored); absent for none. Older apps ignore it.

## Addendum, 2026-10-08: Remind me on a task
One field was added to `task` (additive, LWW): `remindAtMs` (epoch ms; Null or absent = no reminder), set from the task detail's Remind me row on either app. Each device derives a Heads-up notice from it (`TaskReminderRules`, source `TASK_REMINDER`, CLOCK precision per ADR-007) through the notification governor; the notice key holds the time, so a moved reminder reminds again and both devices post under one key. It moves with the task: When (by the same amount between two times, else to the same time of day on the new day), Tomorrow and its undo, Repeat and the next occurrence of a repeating task. Done, Someday and Delete silence it; bringing a task back clears it. Older versions ignore the field.

## Addendum, 2026-10-08: alarms
A new entity type `alarm` (additive, all fields LWW): one per wake morning, id `wake.d<epochDay>` so both devices write the same one. Fields: `kind` (`WAKE`), `day` (local epoch day), `minute` (local minute of the day), `off`, `snoozedUntilMs`, `dismissedAtMs`, `note` ("Standup at 08:00", what it was set for) and `setAtMs`. Setting it again clears the snooze and dismissal; Dismiss on either device ends it on both. The get-ready buffer is `context_mode/alarms.wakeBufferMin` (15–180 in fives; 60 until set). The suggested wake time is derived on each device from the mirrored calendar and work hours (`AlarmRules`), never stored.

*Addendum to the addendum, 2026-10-08 (Alarms, slice 2):* `kind` gains `ALARM` and `TIMER` (quick alarms and timers typed into capture) and two additive fields: `atMs` (a timer's exact moment; `day`/`minute` still hold its local day and minute, so an older reader rings it within the minute) and `lengthSec` (a timer's length). A quick alarm's id is `alarm.d<day>.m<minute>` (typed twice or on both devices, one alarm); a timer's `timer.t<setAtMs>.s<lengthSec>`. `note` holds what it's for, as typed. Cancel sets `off`. Readers that don't know a kind skip the entity. Only text typed into MEKA's own capture field is read as an alarm or timer; shared text stays untrusted and only ever becomes a task (ADR-006).

*Addendum to the addendum, 2026-10-08 (Alarms, slice 3):* `kind` gains `LEAVE` (a leave-by that rings as an alarm) and `event_mark` gains `leaveAlarm` (Bool, additive, LWW: "Ring as an alarm" on the event's Leave by). Nothing is stored to make a leave-by ring: each device works it out from the mirrored event and its marks (`LeaveAlarmRules.alarms`: a travel time, a place that isn't just a link, not all day, not hidden, not yet started) at the start less the travel time, with the id `leave.e<eventId>.s<startAtMs>.t<travelMin>`, so a moved event or a new travel time is a fresh alarm. Snooze, Dismiss or cancel write an `alarm` of kind `LEAVE` under that id (kind, day, minute, `atMs`, note, then the change), so answering on one device ends it on both; a stored `LEAVE` alarm that no longer matches a derived one (the event moved, started, or the switch went off) is ignored. While it rings as an alarm the leave-by heads-up notice isn't posted.

*Addendum, 2026-10-08 (Edit your calendars, slice 2a):* a new entity type `event_edit` (additive, all fields LWW): one change Meka made to a real Google or Outlook event, written by the device that made it (id from the device's id generator) and answered by the server. Device fields: `kind` (`ADD` · `CHANGE` · `DELETE`), `provider`, `account` (email), `eventId` (the mirrored `event`; not for an add), `changes` (`TITLE,TIME,LOCATION,NOTES`, what a change changes), the values written (`title`, `startAtMs`, `endAtMs`, `allDay`, `location`, `notes`: all of them for an add, only the changed ones for a change), the event as MEKA saw it (`baseTitle`, `baseStartAtMs`, `baseEndAtMs`, `baseAllDay`, `baseLocation`, `baseNotes`), `guestsOk` (a delete Meka confirmed although it cancels the event for its guests), `createdAtMs`, `sendAfterMs` (created + 5 s, the undo window) and `undone` (Undo inside the window; only ever set true). Server fields, written once per edit with fixed op ids: `status` (`DONE` · `CLASH` · `REFUSED` · `FAILED`), `statusAtMs`, `detail` (why, in words), `guests`, and on a clash the provider's version (`theirTitle`, `theirStartAtMs`, `theirEndAtMs`, `theirAllDay`). The server sends nothing before `sendAfterMs` + 2 s, never an undone edit, and checks the provider's copy against the base first (CalendarWriter, ADR-009). The server's `event_mirror` gains `remote_id` (migration V9) so an edit can find the real event.
