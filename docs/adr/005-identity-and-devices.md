# ADR-005: Identity, device keys and sessions

**Status:** Accepted, 2026-10-01

## Context
There is a single owner today, and the owner's wife may be a user later (ADR-008). Stolen-device and compromised-cloud scenarios are in the threat model. No API keys may ship in client binaries.

## Options
- **Cognito user pools.** Managed, but heavy for one user, and passkey support comes through its own hosted UI flows.
- **Third-party auth such as Auth0 or Clerk.** Adds a SaaS dependency and a subscription, which is against the product philosophy.
- **Self-hosted passkey (WebAuthn) for people + per-device Ed25519 keys for devices.** A small surface and strong security.

## Decision
- **People:** a `Principal` (person account) authenticates with a passkey (WebAuthn).
  - The server verifies it with a maintained WebAuthn library, pinned in `backend/`.
  - The first enrolment is bootstrapped by a one-time enrolment code printed by the deploy pipeline.
- **Devices:** each device generates an Ed25519 key pair in hardware-backed storage (Android Keystore, macOS Keychain/Secure Enclave where supported).
  - Enrolling a device requires an authenticated principal session and produces a `Device` record.
- **Requests:** every sync request is signed by the device key over method, path, body hash and timestamp.
  - The server issues short-lived (15 min) access tokens bound to the device.
  - Revoking a device invalidates its tokens immediately and stops sync.
- **Recovery:** a recovery key (a 24-word phrase shown once) can enrol a new device if both devices are lost. Restore drills are part of the V1 checklist.
- **App lock:** biometric/device credential on open and after N minutes in the background. This is separate from DB-key authentication (ADR-002).
- **Integration secrets:** no provider API keys ship in clients. OAuth for integrations runs server-side (authorisation code + PKCE), and refresh tokens stay in Secrets Manager.

## Consequences
- **M0, as built:** each device gets a random 256-bit bearer secret at enrolment.
  - The server stores only its SHA-256 and binds every request to that device and household.
  - Revocation is immediate.
  - This is tested in `SyncApiTest`.
- **Before any real personal data reaches the cloud:** Ed25519 request signing and passkey enrolment replace the bearer secret. Until then the cloud stack holds test data only.
- Multi-user later means adding principals to a `Household` with roles. No redesign is needed.

## Amendment 2026-10-01: enrolment
- **Enrolment code.** `POST /v1/enrol`, authorised by a 48-character enrolment code that CDK generates in Secrets Manager (`meka-os-<env>/enrol-token`). The endpoint is disabled when no code is configured.
- **What a device gets.** Each device receives its own 256-bit secret, shown once, stored on the device and kept server-side only as a SHA-256 hash.
- **Re-enrolling** a device id rotates its secret and clears any revocation.
- **Revoking everything.** To revoke all future enrolments, rotate the enrolment code. To revoke one device, revoke that device.
- **Household.** Both devices use the household id `home`.

## Amendment 2026-10-07: device keys as built, and what the enrolment code may do
- **Device keys.** Devices sign with **P-256 ECDSA** (SHA256withECDSA), not Ed25519: it is what the Android Keystore's StrongBox/TEE and the Mac's Secure Enclave both hold in hardware. Each request signs `MEKA1 · method · path · time · nonce · SHA-256(body)`, with a time window and a nonce replay check (`RequestVerifier`). A device registers its key once (`POST /v1/devices/key`, signed with that key); after that its unsigned requests are refused. The bearer secret stays as a second factor.
- **Where the secrets live.** Fold: Android Keystore. Mac: the signing key in the Secure Enclave; the device id, household, secret and server address in small files sealed with a Secure Enclave key-agreement key (`SealedKeyFiles`), so ad-hoc rebuilds don't trigger Keychain prompts. A Mac without a Secure Enclave keeps the Keychain.
- **The enrolment code is narrower than the server's own enrol path.** `POST /v1/enrol`:
  - never brings back a **revoked** device (403 `revoked`); revocation is undone only on the server (`enrol-device` command), which is the owner's own act;
  - can't start a **second household** once one exists (403 `household`);
  - still re-enrols a device that isn't revoked, rotating its secret and clearing its signing key ("Reconnect" after a lost key or a reinstall that kept the device id).
  The apps show both refusals in words (core `Enrolment.refusal`).
- **Not yet restricted:** enrolling a *new* device id into the household. Passkey enrolment (or approving a new device from an existing one) replaces the shared code for that; until then, rotating the code in Secrets Manager (`meka-os-<env>/enrol-token`) after setting up a device is the way to shut it.

## Amendment 2026-10-10: the family page's browser keys (family sharing with his wife, slice 2)
- **Who.** A family member Meka invites (his wife) uses a small web page served by MEKA's own server (`/family`), not an app and not a device of the household. She is a guest of one shared thing (the shopping list), not a principal: her browser can reach nothing else.
- **The invite.** Meka makes it from a keyed device (`POST /v1/family/invites/create`; list and revoke beside it). The link is `/family#<token>`: a 256-bit random token in the fragment, so it never reaches a server log or a referrer; the server keeps only its SHA-256 (`family_invite`, migration V13, additive).
- **First open = the browser's own key.** The page makes a **non-extractable P-256 key with WebCrypto**, kept in the browser's IndexedDB, and sends `{token, publicKey}` to `POST /family/v1/claim` signed with that key (proof of possession). The first key wins; the same key again is fine (a retried first open), any other is refused (`used`). From then on the token is no use.
- **Requests.** `Authorization: Guest <invite id>` plus the apps' signature headers over the same message (`MEKA1 · method · path · time · nonce · SHA-256(body)`, ±5 min, each nonce once); WebCrypto's raw r‖s signature is checked with `SHA256withECDSAinP1363Format`. No bearer secret: the key is the only credential.
- **Revoke.** `POST /v1/family/invites/revoke` refuses her next request at once and the link can't be opened again. A browser that loses its storage (cleared data, Safari's 7-day limit on a page not added to the home screen) needs a new link.
- **Writes.** Her adds and ticks are server ops (`deviceId` `server`, `by` = her name key) written over each field's current head, so they sync into Meka's Lists like any other change; the page can touch only existing `shopping_item` entities. The page itself is static (CSP `script-src 'self'`, no third-party anything, `no-referrer`).
- **The dinners (meal plan slice 3, 2026-10-10).** The guest's one shared thing becomes two: the shopping list and the dinners. `POST /family/v1/meals` reads the week's dinners (today in London and six days on) and the favourites; `POST /family/v1/meals/add` (`{"text"}`, at most 300 characters, read by the devices' own `MealRules.addPlan`) adds a favourite `meal` (`by` = her name key) or, for a name already there, replaces its ingredients; at most 100 favourites (`full`). Planning a day (`meal_day`) and removing a favourite stay on Meka's apps. The server reads and writes only `FamilyShare.SHARED_TYPES` (`shopping_item`, `meal`, `meal_day`; `meal_day` read only), checked in the one write path. The claim's answer lists `"shares": ["shopping", "meals"]`.

## Amendment 2026-10-10: linking a watch from a keyed device (Galaxy Watch, slice 1)
- **Why.** A Galaxy Watch joins as a device of its own (its own hardware key, its own replica, synced through MEKA's server), so no watch data goes through anyone else's service (no Wearable Data Layer). Typing the 48-character enrolment code on a watch isn't practical, and the code is the broad path this ADR wants narrowed; this is the "approving a new device from an existing one" path for watches.
- **Flow.** (1) The watch makes a P-256 key in its Keystore and a device id `watch<16 hex>` (no "-": a device id is the HLC node id; the first form `watch-…` was refused by every replica and changed in slice 2 before any watch linked), and calls `POST /v1/link/start` (`{deviceId, name, publicKey}`, signed with that key, no bearer): the server answers an 8-digit code that lasts 10 minutes. (2) Meka types the code in Ask → More → Watch on a keyed device (`POST /v1/devices/link`, signed): the server enrols the watch into that device's household **with the key that asked**, so every request it makes is signed from the first. (3) The watch polls `POST /v1/link/status` (signed with its key) and picks up `{householdId, deviceId, secret}` exactly once.
- **Limits.** Only keyed household devices can try codes, each at most 5 wrong codes per 10 minutes, so the 10^8 codes can't be guessed; a code works once; at most 10 links wait at a time (unsigned noise can't grow the list); a start must be signed by the key it names; only ids shaped `watch…` can join this way; a revoked watch id is never brought back (a reset watch makes a new id).
- **Where it lives.** Waiting links and the secret between approval and pickup are held in the sync task's memory only (at most 10 minutes), like the verifier's nonce cache: no new table, nothing stored but the device row the enrolment writes. A restart just means the watch asks for a new code.
- **Unlink.** `POST /v1/devices/watches` lists the household's linked watches (id, name, linked time; never a secret or key); `POST /v1/devices/unlink` revokes one at once. Both need a keyed device.
- **The watch's side (slice 2, 2026-10-10).** The Wear OS app (`:wear:app`, same application id and signing key as the phone's) keeps the same scheme as the phone: the signing key in the watch's Keystore (StrongBox when present), the replica in SQLCipher with its key wrapped by a Keystore AES key, identity in app-private prefs excluded from backups. The server's address is built in at install (`tools/install-watch.sh` passes `-Pmeka.syncUrl`; a watch has no room to type it), never a secret. The code on screen is kept so reopening within its 10 minutes shows the same one. When a sync is refused as signed out (unlinked from the Fold or the Mac), the watch offers "Link again", which deletes its replica, its identity and its signing key, so it rejoins as a new watch with a new key and id (the server refuses an unlinked id for good).

## Amendment 2026-10-12: the recovery key (build plan V1 "Recovery key", slice 1)
- **What it is.** 256 random bits made on a keyed phone or Mac and shown once as 24 BIP-39 English words (the last word carries an 8-bit checksum, so a mistyped word is caught on the device). It connects a **new** phone or Mac to the household if both devices are lost; the household's data then comes back from the server's op log (ADR-002, ADR-003). It never decrypts anything.
- **What the server holds.** Making a key sends only `verifier` = SHA-256(secret), where secret = SHA-256("MEKA-RECOVERY-1\n" + hex(bits)) (`RecoveryKeyRules`). The server stores the verifier in `recovery_key` (migration V16, additive; one row per household, made-by and used-by device names). A new key replaces the old row. The words and the secret are never stored anywhere but Meka's paper.
- **Routes.** `POST /v1/recovery/set · status` from a keyed phone or Mac (a watch can't make one). `POST /v1/recovery/enrol` from a device with no secret yet, signed with the new P-256 key it registers (proof of possession, like a watch's link; no bearer): `{secret, deviceId, name, publicKey}` → `{householdId, deviceId, secret}` handed over once.
- **Limits.** The secret's SHA-256 must be the household's **unspent** verifier; the device id must be a phone's or Mac's shape and **new** to the household (`taken` otherwise, checked before the key is spent; a revoked id stays revoked), so the key can't take over a device that is still connected. A key that connected a device is **spent**; the recovered device's Settings asks for a new one. At most 10 wrong secrets an hour, server-wide (`wait`). Refusals are `{"error": key · wait · taken · revoked}`.
- **Still open.** The enrolment code remains the other way in until passkey enrolment; the recovery key doesn't replace it.

## Amendment 2026-10-18: the household's Vault key (Vault slice 2a)
- **Why.** Vault documents (passport scans, insurance certificates: slice 2b) are encrypted on a phone or Mac before anything leaves it, so MEKA's server and S3 only ever hold ciphertext. One 256-bit AES key per household (the **Vault key**) does it; this amendment is how a new device gets that key, and how the recovery key gets it back.
- **Made once.** The first phone or Mac to finish a clean sync with no key in the household makes 32 random bytes and keeps them in its own encrypted database as a device-local value (ADR-002 addendum; never synced, never in a backup). The household learns only the key's id (`vault_key` "household": the first 8 hex characters of SHA-256("MEKA-VAULT-ID-1\n" + hex(key))). Two devices making one at the same moment: the household's (last write) wins and the other is set aside unused.
- **Each phone or Mac's agreement key.** A P-256 key-agreement key in secure hardware: the Fold's Android Keystore (TEE, `PURPOSE_AGREE_KEY`; StrongBox's ECDH support varies), the Mac's Secure Enclave (its handle in the sealed files; a Mac without an enclave can't hold the Vault key). Its public half (X.509 DER) is published as `vault_member` (id the device id). A watch has none and never gets the key.
- **Handing it over needs Meka's Allow.** A device holding the key shows each device asking, with a six-digit code (SHA-256("MEKA-VAULT-CODE-1\n" + the asking device's public key)), which the asking device shows too. Only on **Allow** is the key sealed for it: a one-off P-256 key's ECDH with the member's key → HKDF-SHA256 (salt empty, info "MEKA-VAULT-WRAP-1\n<device id>\n<key id>", 32 bytes) → AES-256-GCM (12-byte nonce · ciphertext · 16-byte tag), written as `vault_wrap` (id the device id, with the one-off public key). The receiving device runs the same ECDH with its own key, opens the box and checks the key's id before keeping it. **Not this one** marks the ask refused; the asking device can ask again.
- **What a compromised server could do.** It can't open a wrap (no private key) and can't get the key sealed for a key of its own without Meka allowing a request whose code doesn't match what his device shows. It could withhold or replay ops, or hand a device a different key with a forged wrap: the key's id is shown on every device ("Vault key 4F2A 91D0"), so two devices disagreeing is visible. Signing wraps with the device signing keys would close the last gap and can follow if wanted.
- **Recovery.** Making a recovery key on a device that holds the Vault key also seals the Vault key with HKDF-SHA256(the words' 256 bits, salt empty, info "MEKA-VAULT-RECOVERY-1", 32 bytes) as `vault_wrap` "recovery". The server holds only SHA-256(SHA-256(domain + hex(bits))) of those bits, from which this key can't be derived. A device recovering with the words derives the same key at enrolment (`RecoveryEnrolment`), keeps it locally until the recovery wrap opens, then forgets it. A recovery key made before the Vault key existed doesn't open it: the Vault says to make a new one.
- **Crypto split.** ECDH and AES-GCM are each platform's (javax/Keystore, CryptoKit); HMAC-SHA256/HKDF are the core's (`Hkdf`, RFC 5869 vectors in tests) so both derive identically. Only base64 Strings cross the Kotlin/Swift boundary (`VaultCrypto`).

### Addendum 2026-10-18 — the Vault's copies behind the fingerprint (Vault slice 4)

- **What is locked.** A document's name and expiry stay readable (they are on the plan already: Today, heads-ups); what a copy holds opens only after the device owner's yes: BiometricPrompt on the Fold (strong biometrics or the device PIN, the same prompt as Money), LocalAuthentication on the Mac (Touch ID, else the Mac's password).
- **Where the lock lives.** In the core's memory on each device (`vaultUnlockedAtMs`; `VaultLockRules`): `openVaultCopy` reads, fetches and opens nothing while locked. An unlock lasts while the Vault is open and never more than 5 minutes; leaving the Vault, the app going to the background (Fold) or the screen sleeping / session resigning (Mac) locks it again and closes a shown copy. Nothing is stored or synced. Adding, replacing or removing a copy shows nothing, so it needs no unlock.
- **Not a key gate.** The Vault key itself is not bound to the biometric (it stays in the device's local store, under the database's own encryption, ADR-002); the lock stops a borrowed, unlocked phone or Mac from showing a passport page. Binding the key to user authentication would cost the offline prefetch and Ask's "do I have a copy?" and isn't worth it for this threat.


## Amendment 2026-10-19: a new phone or Mac is allowed from one already connected (build plan M1 "Clean-ups", slice 1)
- **Why.** The enrolment code was still enough to add a brand-new device id to the household (amendment 2026-10-07, "Not yet restricted"). Now a connected phone or Mac has to say yes.
- **When it applies.** `POST /v1/enrol` with the code, for a phone's or Mac's id (`android…` / `mac…`) the household has **never had**, while the household has an **approver**: a phone or Mac that isn't revoked, holds its signing key, and pushed an op in the last 14 days (`DeviceRegistry.hasApprover`, read from `op_log.received_at`). Otherwise the code works as before: re-enrolling a known id ("Reconnect"), a revoked id (still refused), a second household (still refused), and a household with no approver in use (both devices lost; the recovery key is the other way back).
- **Flow.** The route answers **202** `{"state":"waiting","requestId","code","expiresAtMs"}`: a request id (`join` + 128 random bits, known only to the asker) and a six-digit code both screens show, for 10 minutes. The server writes a `device_join` entity (ADR-008 addendum) and wakes the household's devices at high priority, so Needs you on the Fold and the Mac shows "A new Mac wants to join · MacBook Air · code 482 913" on top, with **Allow** and **Not this one**. The answer is `POST /v1/devices/joins/answer` `{requestId, allow}` from a **keyed phone or Mac** of that household (a watch can't answer); Allow enrols the device with the code's own rules and holds its secret for the asker; either answer writes the ask's state, so the card leaves every device. The asker polls `POST /v1/enrol/status` `{requestId}` (with the enrolment code again) every 3 s: waiting · refused · expired · enrolled (the secret, handed over once).
- **Limits.** Asks live in the sync task's memory only (like watch links): at most 10 waiting, one per device id (asking again replaces it), each answered once. A restart just means connecting again. Nothing identifying is logged.
- **What it doesn't stop.** Someone holding the code and a connected device's bearer secret and key — that's the device itself. The six-digit code is for Meka to check the ask on his screen is the device in front of him, not a secret. Passkey enrolment remains a possible later step; rotating the code is still how to shut the code path entirely.
